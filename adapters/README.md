# External-method adapters

These adapters keep benchmark scoring separate from each method's simulator. Each
adapter converts native exports into the file contract in `SPEC.md` and must retain
the method's native state path.

Every reported external entry is checked with the uniform six-part protocol in
[VALIDATION_PROTOCOL.md](VALIDATION_PROTOCOL.md). The tolerance-sensitivity
re-scoring analysis is generated by analysis/tolerance_sensitivity.py and frozen
under results/tolerance_sensitivity/.

For reviewer setup, exact release pins, runner snapshots, source patches, and a
field-by-field fairness trace, begin with
[REPRODUCING_EXTERNAL_ENTRIES.md](../REPRODUCING_EXTERNAL_ENTRIES.md). The files
under `adapters/reproduction/` are the actual runner/patch snapshots used for
the reported profiles, not pseudocode.

## GaussianFluent full entry

The full entry runs frozen GaussianBench initial conditions directly through
GaussianFluent's released Warp CD-MPM core. Seven scenes are graded: A1a, A1b,
A2, A3, A5, C1, and C2-s. Thermal, renderer-specific, captured-asset,
bimaterial-law, and measured-curve scenes remain explicit NA.

The machine-readable results and complete report are in:

```text
results/GaussianFluent_full/report.json
results/GaussianFluent_full/report.md
```

## GaussianFluent native-asset conversion

```powershell
python adapters/gaussianfluent_to_bench.py `
  --native-dir path/to/output/simulation_ply `
  --output-dir results/GaussianFluent_native `
  --rest-cov path/to/rest_covariance.npy
python run_all.py --results-dir results/GaussianFluent_native
```

The converter consumes `sim_*.h5`; it preserves native positions and deformation
gradients, and writes covariance rows only when a matching `cov3D.pt`/`.npy` export
is supplied. Missing covariance is intentional and causes Gaussian-state scenes to
be reported as NA/invalid rather than silently reconstructing an adapter-side state.

## Additional executed entries

The OmniPhysGS and PhysDreamer adapters run benchmark particle sets directly
through their released MPM cores. Both export entrant-native `F`; OmniPhysGS uses
the covariance push-forward in its renderer, while PhysDreamer exports its native
incremental covariance state. Their C1/C2 reports therefore separate position-fit
kinematics from covariance transport conditioned on the exact internal `F`.

Spring-Gaus is entered only where its released contract is sufficient. A1a and
A1b do not require a calibrated continuum constitutive response, so they can be
graded from the released spring graph and persistent velocities. A2, A3, A5, and
B1 require a mapping from the frozen continuum parameters to learned spring/mass
fields; the release provides no such mapping, so those cells are explicit NA.

PhysTwin is graded on A6 with its released Warp spring-mass integrator and a
deterministic native particle body, as allowed by A6's native-body geometry. Its
release hard-codes gravity in the simulation kernel and learns springs per captured
object, so the remaining frozen scenes are explicit NA rather than adapter-authored
reimplementations.

`results/PhysDreamer_frozen_covariance_fault` is a controlled C1 fault generated
by `variants/freeze_covariance.py`. It preserves the native trajectory and exported
`F` byte-for-byte while holding covariance at its frame-zero value. Transport
changes from PASS (0.00489% median error) to FAIL (2.726%), while the kinematic
score is unchanged.

## Physics3D broad entry

Physics3D exposes the same `MPM_Simulator_WARP` interface as PhysGaussian, so
its broad entry runs through the shared bench harness
(`PhysGaussian/bench/run_bench_scene.py`) with:

```powershell
$env:GAUSSIANBENCH_METHOD_ROOT = "...\Representation\external_methods\Physics3D"
$env:GAUSSIANBENCH_SYSTEM_NAME = "Physics3D"
& ...\.venv-physics3d\Scripts\python.exe ...\PhysGaussian\bench\run_bench_scene.py `
  --scene scenes\<scene>.json --out results\Physics3D_broad [--tier-c]
```

Two Physics3D-specific facts are handled by the harness and recorded in every
`meta.json`:

1. **E units.** Physics3D's released `compute_mu_lam_from_E_nu` multiplies E
   by `1e7` (its native ball config uses `E=0.2` for 2 MPa), so scene E [Pa]
   is passed as `E/1e7`. Passing raw Pa makes mu seven orders of magnitude
   too stiff, violates CFL by ~3000x, and crashes with an out-of-bounds p2g
   `atomic_add` (the long-standing "CUDA error 700" blocker).
2. **Material branch.** The benchmark's declared corotated law maps to the
   pure `jelly_base` branch; the released `jelly` branch adds a learned
   Maxwell residual whose zero-modulus case is guarded against a released
   SVD-of-zero fault, and `particle_F_N` is initialized to identity to match
   `particle_F_N_trial` (released loader left it at zero).

Nine frozen scenes are graded (A1a, A1b, A2, A3, A5, C1, C2-s, C4 through the
harness; native-ball A6 through `physics3d_h5_export.py`). Thermal,
bimaterial (single global material id in the released solver, so no
per-particle constitutive-model dispatch), rendering-roundtrip, melt, C5/C6/
C7/C8 triangle-state, and measured-material scenes are explicit NA.

## GASP broad entry

`../Representation/external_methods/GASP/bench/run_gaussianbench.py` runs the
released Taichi pipeline (teddy pseudomesh vertices as particles in the
released taichi_elements `MPMSolver`, GASP's released per-frame triangle
size-control rule after every step, released `Rescale` placement/export) on
the representation-native scenes:

- `a6_freefall_v1`: native gravity along the scene's axis, body metrics in
  native solver units including per-particle `F` read from the released
  solver's own field.
- `c5_triangle_shape_transport_v1`: the frozen released drop trajectory.
- `c6_rigid_transport_v1`: zero gravity, uniform native velocity chosen as
  `D^-1 d` so the exported COM direction equals the scene's declared
  direction.
- `c7_supported_settle_v1`: resting on the released domain floor.
- `c8_impact_recovery_v1`: soft-elastic drop (`E_scale`, a released demo
  parameter) onto the released floor.

Controlled faults: `--fault half_gravity` (A6), `--fault gravity_left_on`
(C6: the released default gravity is simply not zeroed), `--fault
sand_material` (C8: released inelastic material never recovers), plus the
pre-existing C5 threshold fault.

## Spring-Gaus and PhysTwin revisit (2026-08-28)

Both were re-assessed against the v0.6.0 scene set with the same standards
used for the Physics3D and GASP broad entries. Neither can currently be
expanded defensibly:

- **PhysTwin**: gravity is hard-coded in the released simulation kernel, so
  the zero-gravity C6 transport scene cannot run without modifying released
  dynamics; its native structure is a spring graph with no faces, so the
  `area_rel_error_*` columns of the C6/C7/C8 contract have no honest native
  mapping. Its A6 native-body entry (PASS) remains its scope.
- **Spring-Gaus**: same no-faces limitation, plus its released integrator
  exhibits energy growth (+4237% kinetic energy over the 10 s A1a rollout)
  that already produces honest FAILs on both entered conservation scenes.
  Continuum scenes remain NA for lack of a released E,nu to learned-spring
  mapping.

A future edge-only variant of the shape contract (spring rest lengths as the
persistent element structure, declared in meta.json per SPEC 2.6) would open
C6/C7-class scenes to spring systems that expose configurable gravity.
